# Pathlight 开发说明

## 产品定位

Pathlight 是一个本地优先、证据驱动的求职副驾驶，服务于求职者在招聘平台上浏览岗位、主动沟通、跟进和准备面试的真实节奏。

它不是泛用聊天机器人，也不是无人值守的自动投递工具。它的价值是把用户真实的简历经历、岗位信息、沟通结果和求职偏好组织成可追溯的工作流，帮助用户判断：

- 这个岗位是否真的适合我？
- 岗位职责真正的重心和实际工作是什么？
- 我应当如何基于真实经历开场、回答和跟进？
- 哪些岗位已经沟通过、需要行动，或不值得再次投入？

## 目标用户旅程

以 Boss 直聘为代表的平台为例，用户的实际流程是：

1. 浏览岗位，发现感兴趣的职位后先发起沟通；通常要等待对方回复或同意后才能发送简历。
2. 对岗位描述进行研判，理解职责要求的真实重心、日常工作、硬门槛和潜在风险。
3. 招聘方回复后，根据对方问题准备真实、恰当的回答。
4. 记录后续结果：已读未回、沟通继续、已发送简历、笔试/面试邀约、不合适或 Offer。

Pathlight 应在每一个节点减少重复判断和组织语言的时间，但所有对外消息和投递仍由用户确认与执行。

## 核心能力

### 1. 简历资产

- 导入 PDF/DOCX，提取候选事实；仅用户确认过的事实可被 AI 用于对外表达。
- 保留原始简历；AI 优化生成目标岗位版本，不能覆盖原文件。
- 支持查看版本差异、导出和按岗位选择合适版本。
- 简历优化是可选能力；用户可以不优化，直接进入岗位研判。
- 不得虚构公司、项目、职责、成果、年限或投递状态。

### 2. 岗位导入、研判与优先级

岗位输入支持单条或批量的文本、截图、PDF/Word、职位链接和用户导出的职位表。对于 Boss 直聘、猎聘、拉勾等以登录和页面交互为主的平台，浏览器桥接是首选入口。

每个岗位应输出：

- 岗位的真实工作重心与可能的日常工作。
- 硬门槛、加分项、隐性风险和待澄清问题。
- 基于确认事实与求职偏好的匹配证据、缺口和建议动作。
- `优先沟通`、`可尝试`、`暂缓` 三档建议，而非只给一个不透明分数。
- 可编辑的招呼语；语气可选直接、稳重或热情。

批量处理时，先用用户偏好和硬条件筛选，再按证据排序，输出少量值得查看的候选岗位，而不是生成大量低质量文案。

### 3. 求职过程与提醒

岗位状态应贴合直接沟通的平台机制：

```text
待研判
-> 已生成招呼语
-> 已沟通，待回复
-> 已读未回
-> 沟通中
-> 已发送简历
-> 笔试 / 面试邀约
-> Offer / 不合适 / 已拒绝 / 超时归档
```

- `已读未回` 是独立状态，不等同于拒绝；记录最后互动时间，后续再定义归档和提醒策略。
- 同一公司或同一岗位应去重，避免重复解析与重复招呼。
- 对不适合的公司支持记录原因和冷却期，而不是永久拉黑。
- 首页的便签/提醒只展示待行动事项，如待回复、已读未回、即将面试、需要准备的问题。
- 用户可手动记录聊天摘要、结果和后续行动；应用不主动读取、发送或管理平台聊天。

### 4. 岗位上下文回答辅助

当招聘方提问时，用户可以粘贴问题或上传聊天截图。Agent 应组合当前岗位、确认事实、岗位研判和已有沟通，生成 2-3 个回答草案。

- 清楚标记确定事实、推断和表达建议。
- 对外表达引用事实编号，例如 `F003`。
- 关键信息不足时提出澄清问题，不补全或猜测用户经历。

### 5. 行动型仪表盘

第一版仪表盘不追求泛化的简历发送率或邀约率。用户投递方向通常稳定，仪表盘应优先回答“现在该做什么”：

- 待回复、已读未回、待面试准备的岗位。
- 当前优先岗位与其下一步行动。
- 本周新增沟通和新增结果。
- 已沟通公司/岗位的去重提示。
- 面试时间、准备事项和便签。

在足够多的本地记录积累后，再评估是否增加按方向、简历版本或岗位类型的复盘指标。

## 用户偏好档案

偏好应为结构化数据，而非单一自由文本：

```text
目标方向：Agent 开发、AI 工程师
地点：上海 / 杭州 / 可远程
工作模式：全职
经验与学历硬条件：可接受范围
薪资：可选
行业/公司阶段：偏好与排除项
明确不投公司：原因与冷却期
```

这些偏好和已确认事实是岗位筛选、排序、研判和生成文案的唯一业务依据。

## LLM 设计原则

LLM 是能力层，不是产品本身。Pathlight 的价值来自事实约束、求职工作流和本地闭环。

- 无 API Key 时，简历事实库、偏好、规则匹配、状态管理和本地提醒仍可使用。
- 有 API Key 时，解锁结构化 JD 解析、个性化解释、简历优化和岗位上下文回答。
- 每个任务使用独立提示词和 Pydantic JSON schema，例如岗位解析、匹配、招呼语、回答草案。
- 模型输出必须经程序校验：事实编号真实存在、状态为 `confirmed`、枚举和长度合法。
- 事实不足时，模型必须提问或标记不确定性，不能编造。
- 优先使用结构化上下文、SQLite 查询和 FTS；早期不引入完整 RAG、向量数据库或精排模型。

建议的模块边界：

```text
backend/app/llm/
  client.py       # 模型供应商适配
  prompts.py      # 按任务管理提示词
  schemas.py      # LLM JSON 输出模型
  context.py      # 最小化上下文组装
  validators.py   # 事实引用与业务规则校验
```

## 岗位导入与平台边界

长期目标是将大量岗位筛成少量有依据的候选：

```text
岗位来源
-> 岗位数据规范化
-> 简历事实和偏好的硬条件过滤
-> 证据驱动的排序
-> 向用户展示少量候选岗位
-> 用户打开原岗位，并自行决定是否沟通
```

### 主路径：浏览器桥接导入

Pathlight 桌面端通过受限的本机招聘浏览器桥接，服务 Boss 直聘、猎聘、拉勾等公开招聘平台的岗位浏览场景：

```text
用户点击“打开招聘浏览器”
-> 用户自行登录并浏览岗位
-> 桥接端仅观察当前可见的职位详情页 DOM 内容
-> 本地提取岗位字段并加入待确认导入队列
-> 用户确认
-> 保存原始内容与结构化岗位数据
-> Pathlight 去重、筛选、研判并生成招呼语建议
```

桥接端的硬性约束：

- 仅在用户启动专用招聘浏览器并开启观察后读取可见职位详情页；不搜索、翻页或批量浏览。
- 不读取 Cookie、账号凭据、聊天列表或非当前岗位页面内容。
- 用户自行登录；Pathlight 不复用平台会话发起请求，不点击“沟通/打招呼/投递/发送简历”等外部动作。
- 导入前必须展示公司、岗位、地点、来源链接和正文预览；用户确认后才写入本地数据。
- 首版由 Pathlight 启动专用 Chrome/Edge profile 并经本机 CDP 只读连接；扩展作为手动单页导入备选，Tauri 只接收用户确认后的结构化导入数据。

### 辅助路径：手动与批量导入

1. 粘贴职位文本、链接，上传截图、文件或用户导出的职位表。
2. 将大量岗位写入本地岗位队列，先按偏好硬条件和重复记录筛选，再挑选少量岗位做深度研判。
3. 原始 JD、截图/OCR 文本和来源链接始终绑定具体岗位，供用户回看；不依赖 RAG 保存岗位细节。

截图导入优先采用本地 OCR：截图只在本机读取并转换为可编辑 JD 文本。用户确认分析后，文本才会按所选模型服务的隐私与计费规则发送给 LLM。

boss-cli 是 GPL-3.0 的 HR 端自动化工具：它以 Puppeteer/CDP 驱动登录后的 Chrome，读取页面并执行聊天、搜索和打招呼。Pathlight 不复制其代码、不读取 Cookie 或聊天记录、不使用 CDP 操作求职平台，更不自动投递；仅保留未来“用户主动导入当前页面公开信息”的合规桥接评估。

### 后续可选路径：公开岗位发现

只有在来源提供明确授权的公开 API、RSS 或职位 JSON 时，才实现定时扫描。扫描流程参考 CareerOps：先拉取职位标题、公司、地点、发布时间和链接等轻量元数据，在本地去重、过滤和排序；仅对候选岗位获取完整 JD 并进行模型研判。

公开岗位发现是补充，不替代浏览器桥接；它更适合公司官网和公开 ATS，不试图成为 Boss 等登录平台的后台抓取器。

禁止或暂不实现：

- 使用用户招聘平台账号自动搜索、抓取、模拟浏览或规避平台限制。
- 自动登录、批量发招呼、自动发送简历、自动投递。
- CAPTCHA 绕过、凭据收集、反自动化对抗。

若未来某平台提供正式且允许的投递 API，可考虑“逐岗位、用户确认后的 API 提交”。

## 开发路线

### 已完成

- 初版简历事实库、偏好、JD 解析、规则匹配、招呼语、投递记录和操作追踪。
- 前端工作台和独立设置页；密钥存入系统凭据存储，不写入 SQLite 或源码。
- FastAPI 的路由、repository、领域服务和 Pydantic 校验分层。
- Tauri 2 桌面壳可本地编译启动；FastAPI 已可由 PyInstaller 打包为 Windows sidecar，由桌面应用启动和退出回收。
- 本地 OCR 支持批量导入职位截图，保留原截图与 OCR 文本，并建立可校对的岗位草稿。
- 招聘浏览器 MVP：Pathlight 启动专用 Chrome/Edge profile，以本机 CDP 仅观察可见 BOSS 职位详情页；新页面按正文指纹去重，先进入本地待确认队列，再确认写入岗位草稿。浏览器扩展保留为手动备用入口。
- 岗位状态、下一步日期和本地备注已进入领域模型；首页优先展示待确认、沟通、跟进、笔试与面试行动。

### 下一阶段

1. 完善桌面启动、关闭、更新与 Windows 安装包验证。
2. 扩展领域模型：简历版本、公司去重、沟通记录、行动事项和完整状态机。
3. 使用真实 BOSS 页面校正 CDP 字段提取，并验证招聘浏览器、桌面 sidecar 与本机端口的完整闭环。
4. 将岗位匹配接入结构化 LLM 研判、任务提示词和事实校验。
5. 实现岗位上下文回答辅助与面试准备。
6. 在有合规公开数据来源后，再做公开岗位发现与定时推荐。

## 不可突破的产品边界

- 用户拥有最终决定权；Pathlight 只提供分析、草案、提醒和本地记录。
- 所有外部沟通、简历发送和投递均需用户确认与执行。
- 简历、数据库、上传文件、日志和密钥默认保留在本地并排除 Git。
